# DistrictCore ERP

A full-stack enterprise resource planning (ERP) system built to demonstrate practical experience with **enterprise application architecture, Oracle database development, REST APIs, authentication, authorization, and role-based access control**.

DistrictCore is designed around the same fundamental concepts found in large enterprise ERP platforms: centralized data, controlled access, departmental organization, employee management, job positions, authentication, and permission-based authorization.

# Core Architecture

DistrictCore separates **authentication** from **authorization**.

### Authentication

Keycloak is responsible for establishing the identity of the user.

The frontend authenticates through Keycloak using OpenID Connect and PKCE.

Keycloak issues an access token containing the user's identity.

The API verifies:

* JWT signature
* Token issuer
* Token audience
* Token expiration
* Subject (`sub`)

The API does **not** trust an identity supplied directly by the client.

---

### Identity Mapping

After validating the Keycloak token, the backend extracts the user's:

```text
sub
```

The value is mapped to:

```text
USERS.IDENTITY_ID
```

This allows Keycloak to handle authentication while the ERP database remains responsible for application-specific user information.

```text
Keycloak
    │
    │ sub
    ▼
USERS.IDENTITY_ID
    │
    ├── USER_ID
    ├── USERNAME
    └── ROLE_ID
```

This separation allows the identity provider and ERP application to remain independently manageable.

---

# Authorization

Authentication determines **who the user is**.

Authorization determines **what the user is allowed to do**.

DistrictCore uses permission-based authorization.

Examples:

```text
department.read
department.manage
employee.read
employee.manage
user.read
user.manage
```

Routes can require specific permissions:

```text
GET    /v1/departments
        └── department.read

POST   /v1/departments
        └── department.manage

PATCH  /v1/departments/:id
        └── department.manage

DELETE /v1/departments/:id
        └── department.manage
```

This provides a clear distinction between:

```text
401 Unauthorized
    ↓
Authentication failed or is missing

403 Forbidden
    ↓
User is authenticated but lacks permission
```

```text

    │   ├── employeeRoutes.ts
```

### Controllers

Responsible for HTTP-level concerns:

* Request parsing
* Input validation
* HTTP status codes
* Response formatting
* Error handling

### Services

Responsible for business logic and application rules.

Examples include:

* Validating department data
* Verifying department/job-position relationships
* Ensuring referenced records exist
* Coordinating multiple repository operations

### Repositories

Responsible for Oracle database interaction.

This keeps SQL and connection management separate from business logic.

### Middleware

Authentication and authorization are implemented independently from controllers.

```text
Request
   ↓
authenticate()
   ↓
authorize()
   ↓
controller
   ↓
service
   ↓
repository
   ↓
Oracle
```

# Database Design

The database is designed around relational ERP concepts.

Core entities include:

```text
Departments
     │
     ├───────────────┐
     │               │
     ▼               ▼
Employees       Job Positions
     │
     ▼
Users
     │
     ▼
Roles
     │
     ▼
Permissions
```

Foreign-key relationships enforce data integrity at the database level.

For example, an employee's job position must belong to the employee's department.

The application also validates these relationships before performing operations.

# Employee Management

Employees are associated with organizational structures such as:

```text
Employee
   │
   ├── Department
   │
   └── Job Position
```

The application validates relationships between these entities rather than allowing arbitrary combinations.

For example:

```text
Department: Information Technology
Job Position: ERP Programmer
```

is valid when the job position belongs to that department.

An attempt to assign an unrelated job position is rejected by the service layer.

---

# User Management

Application users are represented separately from their external identity.

```text
Keycloak Identity
        │
        │ sub
        ▼
ERP User
        │
        ▼
Role
        │
        ▼
Permissions
```

This allows the ERP to maintain its own application-level authorization model without implementing password authentication itself.

---

# Keycloak Integration

DistrictCore uses Keycloak as its Identity Provider.

The frontend uses:

```text
OpenID Connect
OAuth 2.0
PKCE
```

The backend verifies Keycloak-issued JWTs using Keycloak's JWKS endpoint.

The backend validates:

```text
Signature
Issuer
Audience
Expiration
Subject
```

The API specifically expects tokens intended for:

```text
districtcore-api
```

This prevents a token issued for an unrelated application from being accepted by the ERP API.

# API Authentication Flow

```text
1. User opens DistrictCore
            │
            ▼
2. React redirects to Keycloak
            │
            ▼
3. User authenticates
            │
            ▼
4. Keycloak issues access token
            │
            ▼
5. React sends:
   
   Authorization: Bearer <token>
            │
            ▼
6. Express verifies JWT
            │
            ▼
7. Extract token.sub
            │
            ▼
8. Query Oracle USERS
            │
            ▼
9. Resolve ERP role
            │
            ▼
10. Check required permission
            │
            ▼
11. Execute controller
```

# Security Considerations

Security was considered throughout the application rather than being added as a final step.

Implemented controls include:

* Externalized credentials
* Keycloak-based authentication
* OIDC
* PKCE
* JWT signature verification
* JWT issuer validation
* JWT audience validation
* Token expiration validation
* Database identity mapping
* Role-based access control
* Permission-based authorization
* Protected API routes
* Separation of authentication and authorization
* Database-level relational integrity
* Parameterized Oracle queries

The application deliberately avoids trusting client-supplied identity headers.

For example, the development mechanism:

```http
X-Dev-Identity-Id
```

was removed from the production authentication path in favor of:

```http
Authorization: Bearer <Keycloak JWT>
```

# Example Authorization Flow

A request to create a department follows:

```text
POST /v1/departments
        │
        ▼
Authorization: Bearer <JWT>
        │
        ▼
authenticate()
        │
        ├── Verify JWT
        └── Resolve ERP user
        │
        ▼
requirePermission("department.manage")
        │
        ├── Permission exists → continue
        └── Permission missing → 403
        │
        ▼
createDepartment()
        │
        ▼
departmentService
        │
        ▼
departmentRepository
        │
        ▼
Oracle
```

This keeps security enforcement centralized instead of relying on individual frontend screens to prevent unauthorized operations.
